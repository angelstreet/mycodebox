# mycodebox release notes

The release note of this repo (owner 2026-11-13). Every merged code change (not docs-only) adds one entry at the top of
`## Unreleased`; the done-check reads the merged diff for this file (REFERENCE "Closing review"). Entry form: one line,
what changed and why it matters, ending with `· area: <area>`.

## Unreleased

- **The migration floor reads every ALTER TABLE action, and a login from a header is a claim** — the lane now classifies each action of an `ALTER TABLE` on its own (an unknown action means not additive) and treats a file that creates a function and calls it while applying (`CREATE TABLE ... AS`, a view, a column `DEFAULT`, an index or `CHECK` expression) as not additive. A lease owner action whose login comes from a request header is journalled as `claimed:<login>` instead of `owner:<login>`; who may perform the action is unchanged · area: merge-policy, leases

- **A lost live-layer measurement is measured again** — the GETs of a tile's live video retried three times, but the ffprobe/ffmpeg measurement of the newest segment did not: a slow host under load lost the reading, and the tile came back as "the live video could not be read" (the night of 2026-11-17 read `vpt-nipogi/DEVICE21` that way while its segment measured 196/255 by hand). The measurement now gets a second try before the layer counts as unreadable, so one slow pass is no longer a lost reading (bug-c27e2c95) · area: rtsp-nightly
- **The nightly's pool probe runs in parallel** — the pool entries were probed one after the other, and the three public candidates that time out on port 554 added about 35 s to every night. They are probed in parallel now (the pool file's order is kept in the report), so the pool block costs about the slowest single probe instead of the sum (bug-5473cd69) · area: rtsp-nightly

- **A tile whose live video could not be read is no longer called black** — the capture check read "the live video is dark" from a live layer it could not even read (a fetch or ffmpeg timeout under load): the night's dry run of 2026-11-17 called `vpt-nipogi/DEVICE21` black while its newest segment measured 196/255 (bright) when fetched by hand. A black verdict needs the three signals to agree (dark thumbnail, dark live video, black source frame), so an unreadable live layer is now `unknown` — "the tile's snapshot is dark and its live video could not be read: the tile is not proven broken" — and the night neither repairs nor blames it (bug-4f69009f) · area: rtsp-nightly

- **The nightly now probes its own pool and the report says so** — the pool was read only when a stream was down and a replacement was chosen, so a broken pool source showed up nowhere in the night's evidence and every night session re-probed the pool by hand (six nights in a row). The run now probes each pool entry on every night: a loopback entry from the host that runs it (through that host's ssh alias), the public ones from codebox, and writes a `pool` block (id, kind, vetted, status, vantage) into `report-<date>.json` plus one stdout line (`pool: smoke ok (from vpt-pi4), wowza-bbb timeout (from codebox)`). The pool file is still never edited by the nightly: a failed probe is reported, not acted on (bug-c64fb86c) · area: rtsp-nightly
- **The nightly's dark-snapshot note now carries the luma numbers that prove it** — a tile whose thumbnail is dark while its live video plays is reported as a note, but the line said "the tile's snapshot was dark but the live video plays" without the two values the run had just read, so the reader had to open `report-<date>.json` to see them. The note now reads "(snapshot luma 27, live luma 94)": the line the night prints is its own evidence (bug-6c8bbe31) · area: rtsp-nightly

- **found-bug checks the proof against the repo the bug belongs to** — the proof gate (`--checked-main`) and the possibly-fixed marks only looked at the dashboard's `origin/main`, so a VirtualPyTest bug could not be filed (its sha was refused) and could be marked fixed by an unrelated dashboard commit. A report now carries `repo` (`--repo`, else the endpoint, else the filer's cwd repo); the server checks that repo's `origin/main` (one fetch on a miss). Dashboard filings keep the same gate · area: found-bug
- **A replacement the nightly installs is verified before the night ends** — a source can die minutes after it was put in
  place (2026-11-15: the nightly repaired the black channel `vpt-nipogi/DEVICE31` with "RMC Decouverte", whose playlist still
  answered HTTP 200 while every playback probe failed 6/6 ten minutes later: the signed segments inside had expired), and the
  channel then stayed dead until the next night. The night now re-probes what it installed from the host (5 min later): a source
  that still plays is left alone, a source that is dead is replaced again with the next candidate that plays (the dead one is
  never taken again), and the nightly budget still bounds the night · area: rtsp-nightly
- Bug intake proof gate: `found-bug` / `POST /api/bugs` refuse a filing without `--checked-main <sha of origin/main>`, the exact error and `--tried` (exit 2 with the rule); effort / time reasons and a free equivalent device send a live filer's bug back once; open bugs a main commit may already fix are marked `possiblyFixed` and skipped by the bug drain until checked (`found-bug --checked <id>`); the scorecard shows filed / fixed-by-filer / stale-closed per day, so stale and already-fixed filings stop costing a worker · area: bug intake
- `cbsession` waits for the project's MCP servers before it starts Claude (bug-dfa9f42a): Claude Code connects an MCP server once, at start, so a worker started inside the 15 s of a VirtualPyTest server deploy had no `virtualpytest` tool for its whole life and spent 20 more turns reading code. `scripts/mcp-ready.js` asks each HTTP MCP server of the project until it answers (60 s at most, `CBSESSION_MCP_WAIT`); one still down is named in a warning and in the prompt, with the command-line fallback · area: platform
- Done-but-failed check: a done line with `goal: achieved`, an all-pass `Verification:` block and a reported bug id is no longer sent back for mentioning the filed out-of-scope failure; "goal not achieved / met" still fires (bug-6b6e6440) · area: platform
- Manager wakes: a wake that wrote a decision line about a session to manager-actions.jsonl (how a stop that needs no message is answered) is no longer counted as an empty wake; on 2026-11-16 this takes the harness-caused empty share from 26 of 31 to 8 of 32 (bug-2279681a) · area: platform


- **Scheduled (P3) leases end 2 min after a dev claim or deploy starts waiting** — a stream-wall run held `vpt-nipogi/device50` for 4.3 min against a waiting claim because the guard only stopped renewing and the 10 min TTL ran out. A P3 lease now also yields to a queued deploy and the lease service ends it 2 min after the first `yield` (`yield-grace`); a missed scheduled run is acceptable, a waiting dev claim is not; the rtsp-nightly repair claim is now P3 ttl 10 (was P1 ttl 20) · area: lease-service
- **`found-bug` sends back "needs live tuning on a device"** (bug-171d2ca9) — seven bugs were filed as large/host-or-device with only "needs live tuning on device50" as the reason and the intake accepted them. `POST /api/bugs` now answers 400 with the rule (claim the device with `vpt-lease claim <env> --any <group> --wait`, fix it, `integrate request`) when `why` is large, host-or-device or other-area and the reason is only live tuning or runs on a device; a reason that names a real blocker (host unreachable, device absent, busy, credentials) still files · area: found-bug
- **A channel whose own picture is black is now repaired by the nightly** — the capture-driven repair is live since
  2026-11-15 (`<state>/rtsp-nightly/capture-mode`): a channel whose **own** frames are dark (not just the host's snapshot
  of it) is replaced from the free lists like a dead one, once the safety checks agree (three dark snapshots 10 s apart,
  the tile's live video, and the source's own frames over a window). A file is never replaced, and a host capture that is
  dark while the source plays is only reported · area: rtsp-nightly
- **A session brief no longer repeats the rules its repo already carries** (TASK-239 audit 2026-11-15, bug-4a33bae4) — `cbsession` printed the STATUS table and the goal rule in every prompt (1,914 words for a handover start) while 734 of the 832 words of those two blocks were word for word in the AGENTS.md the same brief tells the session to read, and the ship rule came three times. When the repo's AGENTS.md carries the STATUS table, the goal rule, the fix-first rule and the closing review, the brief now points to it (416 words for a handover start, 228 for a `-t` one); a repo without them keeps the full text. The STATUS table itself is brought up to the owner's rules of 2026-11-12 in its five copies: `done` only with nothing left and nothing unverified, `failed` only after an investigation, with `cause:` and `plan:` in its form · area: sessions
- Manager event filter: time-box alerts and no-progress of a non-Claude session ride with the next wake, a disk alert under 95% no longer closes the batch window, the manager's own undelivered integration result and `cmtest-` probe stops are dropped; replay prints the kinds of the wakes that stay empty (bug-2279681a) · area: platform

- **Image and video files merge with no approval** (owner 2026-11-17: "if i say yes to the agent it must do it without constraint") — the `adds N image/video files (needs --approved-by manager)` floor reason is removed; `--approved-by` is still accepted and still skips the infra-path reason. Still refused: secrets, migrations, sudoers, units, other binaries, red tests, conflicts, a diff over the 2 MB text-scan cap. · area: integration-lane
- **(superseded above) Image and video files merge with a manager approval** (owner 2026-11-15) — the lane returned every new binary file, one line each, and counted their diff headers in its 2 MB scan cap, so the website's 12 3D Learn cards (5,400 WebP frames, 92 MB) could not merge even with `--approved-by manager` (int-1a1def0c18d73f6ed). A new image, video or font file is now left out of the line scan and is one reason (`adds 5400 image/video files (needs --approved-by manager): ...`) that a manager approval clears; other binaries (archives, executables) still never merge, and a media-named text file is still scanned for secrets · area: integration-lane
- **A tile's live layer is judged over a window of the host's recent segments, not over one segment** (bug-37646a38) — the nightly read the tile's live video from the single newest HLS segment, so one dark segment called the whole tile black and the report blamed the host capture: `vpt-nipogi/DEVICE10` read black at 05:48 on 2026-11-15 (thumbnail 16, live layer 27) while the channel itself played (source luma 169), and the browser proved the tile plays again minutes later (readyState 4, the picture on screen). The live layer is now read over the host's last 30 s of segments: a tile that played a moment ago is seen, and a tile that is really black stays dark in all of them (`vpt-nipogi/DEVICE31`, 16/255) · area: rtsp-nightly
- **A file tile is measured against the clip itself** (bug-59664715) — the nightly said a black tile of a looping file was "a dark frame of the clip itself" while admitting in the same sentence that it had never compared the clip's own picture (the source frame was only read for HLS channels), so a file whose capture really was broken would have read the same. The clip's own picture is now measured too (over a window, past a film's black leader) and the report says what was seen: the clip's own dark frame, or a tile that shows something else. A file is still only reported, never changed and never blamed on the capture side · area: rtsp-nightly
- **ghosty-usage no longer grows ~25 MB/h** (bug-1babb8b3) — the tailer read the whole 113 MB ledger (240k rows) as one string at start-up, joined it into another for the compaction write, and re-read and parsed all of it every 15 min for the scorecard; the JS heap stayed flat (~63 MB) but RSS ratcheted up (806 MB 5 min after a restart, 1 GB at 36 h). The ledger is now streamed line by line, the compaction is written in 1 MB chunks and the scorecard keeps only today's rows: start-up peak RSS 808 -> 395 MB, +35 MB -> +1 MB over 12 scorecard posts · area: usage
- **A live channel is judged over a window, not on its first frame** (bug-5ab9d8b4) — the nightly read the FIRST frame of a channel to decide whether the channel itself was black, but a channel can open on a dark frame: the Pluto TV channel of `vpt-nipogi/DEVICE7` starts its ad break on a frame of 17/255 and was called "the channel's own picture is black" while the channel itself played (the browser shows a movie frame, and the brightest frame of a 3 s window reads 103-119). The source is now judged over a window of frames (2 a second, 6 s, sampled again 10 s later if the window is dark), so an ad break no longer reads as a dead channel — and a channel that is really black stays black: `vpt-nipogi/DEVICE31` reads 16 over every window (1, 3, 6, 12 and 30 s). In plain words: a dark first frame no longer gets a healthy channel replaced · area: rtsp-nightly
- **Docs-only work ships in about 30 s, with a 30 min box** — the lane ends a docs-only merge right after the push (no CI wait, no deploy even with `--deploy`; mycodebox pulls live without a restart), and `cbsession` gives a docs task a 30 min box and a "no lease, no deploy" line: int-1a1d97e6aef011feb spent 27 s merging and 3 min 44 s in a host deploy, under a 2 h box · area: integration-lane
- **The unanswered-stop reminder reaches the Claude manager** — it was typed to the first entry of `managerSessions`, the MiniMax standby `mm-manager` (26 reminders on 2026-11-13 never reached the manager); it now goes to the first manager session that is not the failover standby, and stops sent to the wrong session are reminded once to the right one · area: manager-wakes
- **An idle session or Mac no longer keeps a lease, and a waiting stop is answered at once** — a codebox session at its prompt for 10 min with no background job loses its exclusive lease (`idle-release`, note to the session), a Mac holder with no renewal for 20 min and a waiter loses it too (nudge at 10 min, nothing while a run is attached), and a stop on a named-device wait while an equivalent is free gets the claim command within seconds; the 2026-11-11 replay shows 0 wrong releases and the first real releases ran on 2026-11-13: devices held by sessions that were only sitting there (9 idle nudges, 10 waits beside a free equivalent on 2026-11-11) · area: leases
- **New sessions do the work themselves: no workers unless the brief says so** — every `cbsession` prompt now carries the rule, a session started without `-K` cannot start another one (`cbsession` refuses, exit 2; the manager, the dashboard and `-A` automation are exempt), and AGENTS.md states it: sessions waited hours on idle workers for easy tasks · area: sessions
- **A request with nothing new is stopped at the prompt and named as such** — `integrate request` (client scripts v4) refuses a branch with commits origin does not have, or one that is not on origin, before it is queued (`--no-push-check` skips it), and a lane result for a branch already on the target now reads "nothing new: … no commit of yours was merged" instead of "merged <branch> at <another branch's sha>": two such requests deployed nothing and misled a session for ~14 min on 2026-11-13 ([review](reviews/2026-11-13-stb3-variant-hour.md)) · area: integration-lane
- **A stop the manager left unanswered is sent back to it once, and blocking bugs reach it only when the drain cannot start them** — a session stop with no message and no decision line after 10 min is typed to the manager (`stop-answer.js`); chained `manager-wait.sh` wakes are named as wait wakes, not own jobs; a blocking bug filing goes to the bug drain first and wakes the manager only as `bug-drain-cannot`: fewer wakes that do nothing (S7) · area: manager-wakes
- **A refused lease and a failed apply step are no longer the same thing** — the nightly report and the journal tell them apart
  (`lease_not_granted` / `apply_failed`): a claim the lease CLI refused touched nothing and is retried at the end of the night, while
  an apply step that died after the lease was granted is reported as such (the host may be half-changed), so the reader and the retry
  no longer go after the wrong cause · area: rtsp-nightly
- **A busy host lease no longer costs the night a stream** — the first lease wait is short (5 min) and a repair the lease blocked is
  retried at the end of the night with the long wait (20 min), reusing the source that was already probed: the nightly no longer
  gives up on a host another session is holding · area: rtsp-nightly
- **A film that opens on a black leader is not a dead stream** — the probe looks past the leader before it calls a picture frozen,
  and the nightly deletes its scratch file after the apply step: a healthy movie is no longer reported as broken, and the state dir
  no longer fills up night after night · area: rtsp-nightly
- **A night that finds nothing now says how much it looked at** — the nightly report carries `hosts` (`walked`: the hosts the
  servers listed, `read`: the hosts whose config answered), so "no rtsp devices found" can no longer be read as an empty inventory:
  15 hosts walked and 15 read is a fleet without an RTSP source, while 15 walked and 14 read is a host that did not answer ·
  area: rtsp-nightly
- **A loopback pool source can be vetted from the host that runs it, and a missing lease CLI no longer kills the night** —
  `rtsp_check.py --host <host>` (its ssh alias from `RTSP_CHECK_SSH`) and `--ssh <alias>` play a loopback source where the host
  plays it instead of always answering "unverified", and in live mode a `vpt-lease` that is not on the PATH is reported as "the
  lease command could not be run, nothing touched" and the night goes on instead of dying on the first down stream · area: rtsp-nightly
- **A black tile now needs both of its pictures dark** — the nightly reads the tile's thumbnail *and* the live video the browser
  plays (the newest HLS segment, the brightest picture it holds), so a dark moment of a moving clip is reported as a note instead of
  a dead stream, and a looping clip is never blamed on the capture side: the capture-driven repair now replaces a channel only when
  thumbnail, live video and source frame all agree · area: rtsp-nightly
- **The agent runtime's own process-group guard is no longer read as the session's job** — `own-jobs` treats an inline node module
  (`node --input-type=module --eval`) as the runtime's infrastructure, like the `node -e` helper next to it: a STATUS word that merely
  sits inside that command line ("live" in "keepalive", "table" in "system32") no longer pins a `done` line to `running` · area: harness
- **Done-check asks for the release note and the bug record after a code fix** — a `STATUS: done` line after a merged code integration (not docs-only) whose diff has no release-note entry and whose closing review gives no `release note none needed: <reason>`, or whose fix names no bug id in `bugs:`, is sent back once with the two asks. In plain words: a shipped fix leaves a release note and a bug record without the owner asking · area: harness
