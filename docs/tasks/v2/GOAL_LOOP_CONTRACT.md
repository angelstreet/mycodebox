# mycodebox V2 — Universal Goal Loop and Autonomous Task Contract

**Status:** Required product behavior to implement and verify, not a claim about current code. Applies to this refactor AND every task created after the feature ships. This contract supplements `MYCODEBOXV2_AGENT_TASK.md`, `PROMPT.md`, repository `AGENTS.md`, and `docs/CONTRACT.md`; higher-priority safety rules and explicit permissions always win.

## Product outcome

Every task, whether entered via UI/API, scheduled, generated by the manager, or delegated by another agent, gets the same durable goal contract and a continuously evaluated **goal loop**. The default experience is: the owner specifies the desired outcome once, and mycodebox autonomously plans, delegates, implements, tests, obtains an independent evaluation, and repairs/replans until the accepted definition of done is *verifiably true*. The owner is not asked to approve routine decisions. Automatic decisions are explained in a durable, inspectable decision journal. The same machinery must be used to implement mycodebox V2 itself (bootstrap using the launch prompt and files until the engine exists, then dogfood the engine in disposable environments).

**No arbitrary task-wide attempt cap or fixed 3-retry gate.** A goal loop is not permitted to claim success simply because an agent says 'done'; it cannot continue unchecked forever either. Physical limits and safety controls (provider quota, explicit spend authorization, system capacity, user cancellation, permissions, lease failures, or unverifiable evidence) remain binding. These are controls, not quality-based shortcuts. A temporary rate limit leads to backed-off waiting/rescheduling; a blocked privileged action leads to `awaiting_approval`, never implicit authorization. Distinguish `done`, `not_yet_done`, `waiting`, `needs_owner`, `unrecoverable` and `cancelled`.

## Durable task specification (schema requirement)

Required: `task_id`, `project_id`, `goal` (outcome, not just command), `scope`, `prohibited_actions`, `definition_of_done[]`, `acceptance_checks[]` (test command, expected result, evidence type), `risk_class`, `runtime_capabilities`, `privacy_policy`, `resources`, `dependencies`, `base_sha`, `approval_policy`, `created_by`, and `status`. Optional: `priority` (cost/quality/speed), `budget_policy` (explicit authorizations, observed spend, quota-aware throttling), `deadline` when actually assigned, `preferred_models`, `review_policy` and `schedule`. Never invent caps or deadlines as if they were owner-approved. Inherited subtasks cannot weaken parent constraints.

All tasks follow the same lifecycle: `created -> clarified (autonomously if possible) -> planned -> ready -> executing -> evaluating -> (accepted | repair | replan | waiting | awaiting_approval | failed_unrecoverable | cancelled)`. Include explicit `integrating` and `release_verifying` states for delivery. Persist events before acknowledging them and deduplicate idempotently. Store context summaries, worktree/branch/base SHA, parent-child relationships, per-role allocations, evidence and decisions. Reconcile after restart.

## Goal loop — actual decision procedure

1. **Interpret the goal:** derive measurable acceptance requirements, tests, out-of-scope changes, security and permission constraints. If an ambiguity can be resolved safely by a reversible, documented default, choose it and explain why; escalate only mandatory choices such as missing authorization, irreversible risk or unknowable external intent.
2. **Inspect reality:** collect current repository SHA, worktree state, source evidence, tests, leases, runtime capabilities and available capacity. Fail loudly on unavailable evidence; never treat unavailable as zero or passing.
3. **Plan work:** create a dependency DAG, choose roles and model/runtime using capabilities and measured performance. Parallelize only independent tasks in isolated worktrees. Native runtime delegation is optional; mycodebox-owned goal/evidence obligations are invariant.
4. **Execute:** developer may edit within assigned worktree and scope, run approved commands, and checkpoint outputs. Record attempted external effects with idempotency keys and reconcile unknown outcomes before repeating.
5. **Deterministic verification:** run applicable unit, integration, contract, E2E, security and non-regression tests on an identified SHA. Fail the gate on missing required tests, failing assertions, altered permissions or unknown test results. Store exit codes, test artifacts and redacted reproducible traces.
6. **Independent evaluation:** a separate verifier reviews the diff and evidence against original requirements. It may recommend more tests or changes; it cannot self-certify actions it authored. For judgment-heavy items, use an evaluator with a rubric and source evidence, with human approval only where the policy requires it.
7. **Feedback and next action:** if all criteria pass, mark `accepted` and hand off to Integration for authorized release gates. Otherwise classify failures: implementation bug -> targeted repair; repeated same failure -> change plan/harness/model; flaky test -> isolate and resolve root cause; provider unavailable -> backoff/fallback; infrastructure -> incident to System Operations; lease unavailable -> wait; unauthorized action -> request approval. Explain each selection, rejected alternatives, and evidence.
8. **Repeat and persist:** checkpoint every transition; revisit pending items when dependency/lease/quota recovers. Do not loop aggressively without evidence of a meaningful next step. Waiting and blocked are not PASS or terminal success. Always allow owner cancellation.

## Decision policy — feedback only when necessary

Autonomously select the best *permitted* action when it is reversible and testable. Log `decision_id`, alternatives considered, chosen option, evidence, expected effects, rationale, model/runtime, confidence calibration (if available), rule/approval policy and rollback. Emit concise milestone reports, not questions for routine technical tradeoffs. Ask owner only for: new/expanded permissions or credential access, changed scope or business intent that cannot be inferred, irreversible/destructive changes, merge/push/deploy where separately required by project policy, explicit owner preference without safe default, or risk/cost that exceeds **authorized** resource boundaries. A recommendation is not permission; never convert silence into approval. Unknown external state is a block until reconciled.

## Role delegation and ownership

- **Manager:** deterministic authoritative state machine; selects and supervises agent runs; its LLM consultants recommend but cannot override policy.
- **Planner:** drafts the approach and tests; no write to shared branches.
- **Developer(s):** implement in isolated worktrees, no direct merge/push/production or privileged maintenance.
- **Independent Tester/Verifier:** run checks and review evidence, independent context and checkout.
- **Integration Agent:** owns integration lease, assembled commit, full local/remote CI checks and authorized merge/push; does not bypass required checks.
- **System Operations Agent:** owns resource and service incidents with host/service leases; may perform only explicitly preauthorized reversible recovery, otherwise pauses and escalates.
- **Security Reviewer:** inspects elevated-risk changes and release gates.

Provider-neutral roles, runtime-specific adapters. A task may use Claude Managed Agents or Claude Code native subagents, Codex or OpenCode native agents, or mycodebox-created subprocess workers. Nested subagents inherit parent isolation, data policy, budgets and goal. Parent must receive verified child artifacts and may not trust textual claims. Provider failures must not erase persisted task state.

## Leases, safety and release

Acquire an atomic lease with fencing token for each mutable shared resource; absence of a lease is not proof of availability. Task-specific worktrees are isolated. Integration branch and main shared mutations, deployment, host-wide maintenance and service restart each have separate lease requirements and approval policy. Never push/merge/deploy just to satisfy a goal without explicit applicable authorization. Before a protected operation, recheck current head SHA, evidence, required CI, permission, approval and fencing. Preserve existing repository restrictions (Tailscale-only, no secret leakage, forbidden topics, normal CLI permissions, fail-closed restart).

## Required automated tests (add these to V2 CI and evidence ledger)

- GL01: task created by UI/API/schedule/agent all get equivalent goal contract and loop.
- GL02: first implementation fails deterministic test; agent receives structured feedback, changes code, re-runs, passes on exact SHA, independent verifier approves; no arbitrary 3-attempt cutoff.
- GL03: repeated identical failure triggers replan/harness improvement and evidence-based model choice, not identical blind retries; simulate at least four consecutive failing iterations before eventual success.
- GL04: missing test artifacts or unavailable evaluator produces `waiting`/`blocked`, never `completed`.
- GL05: independent reviewer rejects a superficially passing patch; developer repairs; checks rerun.
- GL06: provider outage, rate limit, context exhaustion and process crash preserve task state and resume idempotently.
- GL07: no-progress loop uses diagnostic replan/backoff/suspend, without false success or runaway execution.
- GL08: every automatic decision has structured rationale, alternatives, evidence and undo/retry guidance; no owner question for safe reversible choices.
- GL09: credentials, protected merge/push, production deploy, destructive host repair require explicit policy authorization regardless of the goal text; quiet owner never counts as approval.
- GL10: leases race/stale fencing fails closed; Integration/System Ops coordinate to avoid conflicting resource mutations.
- GL11: cross-provider execution with nested native delegation and ordinary worker fallback satisfy identical acceptance checks.
- GL12: reopened task after crash/merge conflict/upstream change revalidates evidence against current SHA; never trusts stale passing CI.
- GL13: costs and tokens measured where available; unknown usage stays unknown; throttle/wait when authorized resources are exhausted, without inventing or silently extending authorization.
- GL14: end-to-end disposable repo: task intake -> worktree -> multiple repair loops -> independent verifier -> integration staging -> CI-equivalent verification -> accepted/release-ready; inspect UI and machine-readable trace.
